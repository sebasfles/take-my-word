# 0005 Desktop release and updater

## Goal

A user downloads the Windows installer from the landing, installs it, and from then on the app offers each new version itself.
This task turns the desktop shell from 0002 into something distributable: a release workflow on tags, a signed updater manifest, and the update dialog in the app.

## Scope

- `.github/workflows/desktop-release.yml`: on tags `desktop-v*`, build the Windows NSIS installer with `tauri-action` on `windows-latest`, sign the updater artifacts with the Tauri updater key, publish a GitHub Release with the installer, `latest.json` and release notes from the tag message. No AWS access.
- Tauri updater plugin configured with the public key and the endpoint `https://github.com/sebasfles/take-my-word/releases/latest/download/latest.json`; the app checks on startup and every 6 hours, shows a dialog with the version and notes, and installs on the user's yes; "Later" postpones to the next check.
- Updater private key generated by the crew, stored as the Actions secret `TAURI_SIGNING_PRIVATE_KEY` (and its password) through the GitHub App or `gh` as sebasfles, never committed; the public key in `tauri.conf.json`.
- Versioning: `apps/desktop` version from `Cargo.toml` and `package.json`, kept equal, checked in CI; a `pnpm release:desktop` script that bumps both, commits, tags `desktop-vX.Y.Z` and pushes.
- The landing's download button points to the latest release asset path once the first release exists (`releases/latest/download/<installer name>`), updated in `apps/web`.
- First release `desktop-v0.1.0` published from `develop`'s desktop at the end of the task, so the landing has a real installer.
- Screenshots: update dialog at the three widths in the workspace.
- Docs: desktop and infra module docs via `document-task`; TRD desktop section.

## Out of scope

- Code signing certificate for Windows (SmartScreen warning stays in v1).
- macOS and Linux builds and notarization.
- Delta updates, release channels, rollback.
- Deferred: hosting installers on AWS.

## Acceptance

1. `pnpm lint`, `typecheck`, `test` at the root and `cargo fmt --check`, `clippy`, `test` in `apps/desktop` pass; `ci` green on the PR; `desktop-ci` still attaches the installer artifact.
2. Pushing tag `desktop-v0.1.0` runs `desktop-release`, which publishes a GitHub Release with the NSIS installer, its `.sig`, and a `latest.json` whose signature verifies with the public key.
3. Installing `desktop-v0.1.0` on Windows 11, then publishing `desktop-v0.1.1` (a dummy change), makes the running app show the update dialog within 6 hours or on restart; accepting installs 0.1.1 and relaunches; "Later" keeps 0.1.0 running. Verified by the crew on the Windows side with screenshots.
4. The landing's download button downloads the latest installer.
5. A mismatch between `Cargo.toml` and `package.json` versions fails CI.
6. No private key or password appears in the repo, logs or PR.

## Approach

- `tauri-action` with `tagName`, `releaseName`, `includeUpdaterJson: true`; alternative rejected: hand-written release scripts.
- Updater plugin `tauri-plugin-updater` with `dialog` off and a custom dialog in React so the copy is ours in Spanish and English; alternative rejected: the plugin's built-in dialog (English only).
- Secrets through the Actions repository secrets, created with `gh secret set` as sebasfles; alternative rejected: environment secrets, since releases are not per env.

## Database

None.

## Infra

GitHub only: repository secrets `TAURI_SIGNING_PRIVATE_KEY`, `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`; workflow permissions `contents: write` for the release job. No AWS.

- Windows machine rules (from 0002): the toolchain (VS Build Tools 2022, rustup, fnm with Node 24, pnpm) is installed; this task keeps its own mirror checkout at `C:\dev\tmw-0005` and its scratch under `C:\dev\tmw-0005-*`, all removed at clean-task. Injected runs (keystrokes, mouse, foreground window, microphone setting) need Sebastian away: start only after 2 minutes of Windows idle, abort and restore on real input, and announce each run to the om-manager with `computer busy: <what, how long>` before and `computer free` after, restoring debug apps, hotkey, autostart, microphone setting and clipboard. Another desktop task may run in parallel: never touch its mirror, and never start an injected run while the om-manager has not relayed the other task's `computer free`.

## Design

None; one dialog designed in code.

## Risks

- `tauri-action` build time on `windows-latest` is long (15 to 25 min); acceptable.
- Two releases are needed to prove the update path; the dummy 0.1.1 is real and stays as the latest.
- SmartScreen warns on unsigned installers; documented.

## Context & decisions

Consolidated 2026-10-21; answers by Sebastian through the om-manager unless marked (om-reviewer).

- Release timing: build and review everything now; dry-run `desktop-release` on a draft release to prove signing and `latest.json`.
  No public release of the stub shell: once 0007 is on `develop`, rebase, build the release with 0007's prd config, then cut `desktop-v0.1.0` and `desktop-v0.1.1` on this branch and run Acceptance 3. The PR waits for that.
- Releases are prd builds; dev and prd landings link the same installer. The release job uses no Actions environment (prd's deployment policy allows only `main`).
- Tagged commits stay untouched: PRs merge with merge commits, so the tagged commits reach `develop`; after a tag is pushed, never rebase or force-push at or below it.
- Scope adjusted, `pnpm release:desktop X.Y.Z` (root): refuses `develop` and `main` and a dirty tree; bumps `apps/desktop/package.json`, `Cargo.toml` and the package's entry in `Cargo.lock`; commits; creates the annotated tag `desktop-vX.Y.Z` carrying the notes; pushes branch and tag. Reason: `protect-develop` requires PRs (`infra/environments/core/github.tf`).
- Updater key: generated outside the repo, password never in argv; both secrets set with `gh secret set` from stdin; both values appended to the root `.env` and the workspace `.env`; temp files deleted. Sebastian copies them to his password manager (om-manager tells him).
- Landing (om-reviewer): the release also uploads the installer under a fixed name without the version; `apps/web/src/lib/links.ts` points to `releases/latest/download/<fixed name>`, since Tauri's installer name carries the version.
- Versioning (om-reviewer): `tauri.conf.json` drops `version` so Tauri reads `Cargo.toml`; the equality check runs in `ci` (the required check); `desktop-release` fails when the tag differs from the app version or the tag has no message.
- Signing (om-reviewer): only `desktop-release` sees the key; `createUpdaterArtifacts` is enabled for the release build only, so `desktop-ci` keeps building the installer without secrets.
- Updater (om-reviewer): check and install run in Rust; React only renders the `update` view and answers through commands, so the WebView gets no updater permission. Updater off in debug builds. Tauri 2's plugin has no built-in dialog, so "dialog off" is moot.
- Update window (om-reviewer): opens without taking focus, never during a hold or before a pending paste lands; install only when idle; release notes rendered as plain text. Copy in es or en from the Windows language, mapped as `src-tauri/src/locale.rs` (es fallback); the rest of the UI stays English (tracked for 0008).
- Acceptance 3: the 0.1.1 bump alone is the dummy change.
- gh (om-reviewer): every gh call runs as sebasfles with `GH_TOKEN="$(gh auth token --user sebasfles)"`; the active account (sflores-designli, no push) is never switched.

Constraints:

- `docs/modules/desktop/ard.md` "Updates through GitHub Releases"; `docs/modules/infra/ard.md` "Terraform owns infrastructure": no Terraform, no AWS.
- Rust checks from WSL with `TMW_WINDOWS_CHECKOUT='C:\dev\tmw-0005'`; never touch 0007's mirror; Windows idle and `computer busy`/`computer free` rules from Infra.
- 0007 touches `tauri.conf.json`, `Cargo.toml`, `Cargo.lock`, `lib.rs`, `windows.rs`, `main.tsx`, `view.ts`: keep changes there minimal; the rebase resolves them.

Review focus beyond the Pipeline:
- No key, password or token in the repo, workflow logs, `verify.log`, screenshots or PR; `contents: write` only on the release job.
- The update window never steals focus from the paste target.
- `latest.json` signature verified against the committed public key, with evidence in the PR.
